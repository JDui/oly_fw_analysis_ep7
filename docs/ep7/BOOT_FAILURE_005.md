## 软件排查：事实与假设

1. `runtime/cold_bootstrap.c` 会在原厂 `60191371` 调用位置检查当前任务、冷启动
   上下文、安装组、私有锁及五个队列；失败进入 `0xf01..0xf06` 终止分支。
   `runtime/quarantine.s` 清除本核普通中断使能位，并永久循环。该行为能够阻止
   后续原厂任务启动、造成黑屏，但尚未从机身取得证据证明命中了哪一分支。
2. 原厂 `60030afa` 的任务初始化把 TCB+48 设为 1；原厂段初始化 `6004586c`
   使用 `1 << (段号 - 1)` 并在结束时合并到 `a272e41c`。这支持两项检查的静态
   来源，但不证明现场值在新增 bootstrap 时仍然符合全部假设。
3. 交付前的启动模拟显式提供当前任务、就绪/等待链表及队列对象/缓冲区；未执行
   完整内核静态对象创建、物理缓存/多核时序或整机启动。下节针对原生静态分配补充
   检查，仍未得到运行到该 bootstrap 的真实机身状态。
4. 原厂启动前缀保持相同、容器被原生更新器接受、加载复制及局部 GUI/worker 模拟
   通过，都没有验证新程序在实机的完整启动。这次故障不被历史通过项覆盖。

## 006：未绑定拍摄任务时的误停机修正与故障提示

在保留005镜像上，用既有原生引擎完成 bootstrap 发布后，保持模型中的Usr3任务，
调用`ep7cn_engine_epoch`：584条指令后到达`_ep7_gcc_quarantine`，D0=`0xe03`。
此时尚未选择拍摄任务、也没有扩展持有的拍摄对象。005将“运行时已经发布”错误地
当成了“拍摄任务已经接管”，对未接管的异任务调用也关闭扩展并永久停机。

006只调整这一个分支：尚未选择拍摄任务时，外部原厂调用保持中性；已经选择所属
任务后的破坏性异任务调用仍停在`0xe03`。参考fishcu先确认所属对象、再处理扩展
状态的方式，不引入另一套分配器、消息通道或虚拟机。

[006定向报告](../../research/ep7/candidate-006-boot-guard.json)执行最终候选字节：
实际`6029ce9d`补丁调用/桥接在611条指令后进入原厂`6029acd8`，输入寄存器与扩展
状态保持；未接管时的外部注册不再关闭扩展；合法controller随后可加入；已绑定后
异任务reset仍以`0xe03`停止。**这个调用是针对性的离线反例，不是实机开机追踪，
不能据此断言005现场一定命中了它。**

006还保存首次终止码，并通过原厂`601e73e5`（channel0/250ms）尝试AF闪烁提示。
复用更新器已存在的函数与CALL栈约定；原函数指令、五次底层调用顺序和配置参数已
执行核对。底层PWM/时钟返回仍为模型，没有声称LED实测成功。原服务不可用时仍可能
无提示停机；未见AF闪烁不能排除终止分支。普通开机时的此提示不是刷写完成指示。

排查中另做了普通队列入口原厂/005寄存器对比：receive入口的算术标志差异会在下一
个条件分支前被原厂指令覆盖，没有由此证明ABI故障。实际COLOR构造探针推进到选择器
扩容及后续原厂服务后，停止于未建模的原厂内核共享锁；此结果不算完整GUI构造通过，
更不是005实机错误证据。没有将这些假设加入006修复。

006的H/L编辑/冻结、worker系数、加载及SD入口隔离均针对最终链接重新验证。容器
继续复用fishcu；全组件加和校验和内容回读完成，原生mode1写入路由及错误停止完成。
按本轮最小必要测试要求，没有重复未改动的完整原生mode2解码；005的mode2通过不
