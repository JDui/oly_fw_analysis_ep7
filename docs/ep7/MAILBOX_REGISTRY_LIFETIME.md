# 动态 mailbox 管理槽与发布窗口

2026-10-31。继续[mailbox FIFO 审计](CONTROLLER_MAILBOX_ORDER.md)，只追踪其中未决的
6077973a 管理对象来源。没有重做 FIFO、运行整包固件或修改原厂代码。

## 两种 ID 与正常句柄来源

全局61fa8f98保存一个独立注册表指针。6077957a初始化包装器创建容量32的注册表；
6076dd8e用`base + (id-1)*28`查槽。60a7ff68的四项虚表分别指向创建607795b7、
删除6077973a、接收607797c8、发送6077988a。它与内核的mailbox对象表不是同一数组。

|槽字段|本次确认的用途|
|---|---|
|+0 byte|已占用标记；不能独立视为初始化完成|
|+4 word|原始内核mailbox句柄|
|+8起|可选名称；reserve向这里发起最多15字节的复制|
|+24 word|消息池辅助对象指针|

创建API可接受指定的**注册表ID**，先调用6076ddab预留槽，再建立消息池。
它随后以全零配置调用原生6003032f创建mailbox。6005379c保留原始返回值；
只有正返回值才在60779708写入槽+4。辅助对象指针填好后，60779714才把注册表ID
写给调用者。用户输入的注册表ID没有直接写成原始mailbox句柄。

删除API查到槽后仅检查非空和+0非零，然后从+4取原始句柄，符号扩展低16位，
于60779774调用6003769a。一般接收和发送包装器也通过该槽的+4访问内核邮箱。
本次全main字面量扫描找到61fa8f98的11处引用；唯一直接存储在607795ad。
这不是所有派生别名或其他组件写入的排除证明。

## active 早于完成发布，释放保留旧句柄

6076ddab只在选择槽时持有内部锁。自动选择路径在6076ddde设置+0=1，指定ID路径
在6076de0b设置+0=1；可选名称复制后即解锁并返回。后续消息池与mailbox创建、
槽+4/+24赋值和向调用者输出ID，均发生在此返回之后。

6076dd48释放槽时清除名称首字节、+24和+0，**不清除+4**。所以已预留槽可能包含
零句柄，或者上一个使用周期留下的句柄。不能仅凭active把该槽当作已完成发布的对象。

复用严格GNU执行器的两组定向现场：第一个槽已占用，第二个槽未占用，其+4分别为
0和2。每组执行原厂reserve内部35条指令，只把第二槽+0从0改为1，+4保持不变。
再以同一个槽作为lookup结果，执行原厂delete前缀8条指令，两组均到达原始delete
调用前，D0分别为0和2。总计4次短执行，未调用内核删除。

执行从锁调用之后开始，在解锁之前停止；delete从lookup之后开始。锁、分配器、
名称复制、真实调度和完整初始化均未执行。这里证明的是原厂局部发布窗口，
**不是已经在相机上触发的并发错误**。正常调用者等待create成功再使用ID仍可避开窗口；
旧ID持有者或指定ID并发访问是否可达，需要调用者层证据。

## 对捕获通道结论的影响

在注册表正确初始化、所有+4写入均遵循上述create路径、内核slot1一直占用、
且没有其他删除/别名写入路线的条件下，自动创建只返回空闲mailbox，无法产生原有
mailbox1的句柄。这给出了有限路径下的排除推导；尚未证明所有这些前提在全系统成立，
因此不把mailbox1提升为“永不删除”，也不据此宣布callback互斥或G1/G3通过。

后续优先追踪type7/type39完成回调的实际执行域与取消汇合。新代码不得把这里的
active位当作生命周期租约；其安全性仍依赖自身冻结值、撤销和已证明的访问资格。
