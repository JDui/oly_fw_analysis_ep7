# 删除后的队列 ID 可被自动重用

2026-10-31。本次核对66条原厂指令及两个配置项，见
[probe](../../tools/ep7_queue_recreation.py)和
[结果](../../research/ep7/queue-recreation-current.json)。只读，没有相机执行。

原厂root600411a4的+60指向600410d8，其queue limits半字为：+24=0、+26=255。
这不是“已知4b/4c/4d/ab/4f都处于保留静态范围”的配置。自动分配覆盖1–255，
包括全部五个pipeline handle。

实际路径为：

1. 创建入口60030269检查spec，进入critical区后在600302bd清零d0，以auto-ID调用
   6003541e。不是只分析了一个没有调用者的通用helper分支。
2. helper从root+232对象表读取候选ID；object+0为零即可选中。扫描越过上界时，
   从limits+24加1重新开始。本机该值为1。
3. 成功后把调用方新spec的四个word写入queue+20..35，再调用60030c4c分配/初始化
   backing。maximum和ring来自本次创建，不能假定与先前实例相同。
4. 已核对的删除路径释放backing后把object ID清零；因此原先的pipeline ID有条件地
   再次成为自动选择的候选。这里没有声称实际观察到运行时重建。

这给出了现有queue快照检查的具体限制：检查成功后若发生删除及重建，后续无capacity
参数的raw receive可能面对另一个实例。相同handle、相同object地址、甚至两次读取
一致都不能独立排除这种间隙。`ep7r_stop`也只停止之后的实验producer准入，不能阻止
原厂其他组件创建queue。

下一实施必须落实队列存活合同：在已发布期间禁止这些实例被删除/重建，或者实现能
证明所有在途I/O静止的退出协议。选择前继续审查真实删除调用者和普通退出/故障退出，
避免把正常关机变成无条件保持；不能仅把失败视图改成true以通过安装检查。

若选择在allocator扫描中跳过保留ID，还必须同步处理容量计数和“无可分配槽”终止：
原厂满池判断使用实际占用计数，单独跳过空洞可能使计数与可选槽数不一致。这不是
本次已采用的修改方案。当前runtime仍要求G6提供存活资格，未安装任何hook。

本次只新增必要的原厂静态证据，没有更改生产C/汇编，因此不重复host或对象编译。
G1/G2退出闭包与G6安装仍未完成，整体固件编译未开始。
