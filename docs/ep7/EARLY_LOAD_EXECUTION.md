# 早期装载：三段读取、条件回放与失败返回

复用现有 `penf_code_space_load_probe.py` 的加载/执行/重载方法，以及
[严格GNU引擎](STRICT_SIM_ENGINE.md)的Region协议；地址和原指令全部来自E-P7。
没有调用PEN-F固件读取或SHA入口，没有增加CPU或NAND实现。

## 新确认的边界

原厂 `600201db..600201f9` 实际生成参数并调用 `6002144e`。
在readiness三个字节均为0、日志计数100、静止计时器的明确fixture下，
包装器把657,408字节分成三次底层请求，顺序和范围如下：

|底层入口|逻辑flash|非缓存目标|字节数|
|---|---|---|---:|
|60020ba7|406b0000|a0030000|65,536|
|60020dc0|406c0000|a0040000|524,288|
|60020ba7|40740000|a00c0000|67,584|

第一处代码候选 `60048040..6004ffc0` 落在第二次读取内；第二处
`600c8040..600cffc0` 落在第三次读取内。成功读取模型下，两处RAM标记均被完整加载，
各自9字节哨兵经GNU CALL/MOV/RET返回预期值。随后只扰动两处候选，再运行同一原厂
包装器，整段657,408字节准确恢复为同一逻辑源，候选外边界保持原厂内容。

**原厂返回0不能证明搬运成功。** 将三次底层读取均改为“没有写任何目标字节，返回
`ffffffff`”的失败契约后，原厂包装器仍返回0，目标完全保持初始字节。具体是：

- `6002151f` 第一次读取返回的D0在 `60021524` 被栈中目标指针覆盖。
- `60021540` 第二次读取返回的D0未检查，接着计算剩余范围。
- `6002155d` 第三次读取返回后按剩余长度分支；`600215ea` 又调用计时器。
- 最终 `6002161d` 明确清D0，再返回到 `600201fe`。

这证明包装器对**会返回的底层错误**不传播状态；没有证明实际NAND错误会走该契约，
也没有推断底层诊断一定返回。冷安装审查不得把到达 `600201fe` 或D0=0单独当成
新增代码已驻留的证明。

## 模型与原生执行分界

[探针](../../tools/ep7_early_load_probe.py)核对34条精确指令，执行经过99个不同原厂地址。
原厂调用点、拆分算法、readiness检查、计时包装器和返回路径由GNU核心执行。
仅在 `60020ba7` / `60020dc0` 入口截停，由fixture按已核对请求搬运逻辑源或注入失败；
随后从各自原厂RET继续，让原指令恢复保存寄存器和44字节frame。
没有伪造整个loader直接完成。

诊断开关 `61b213a4` 的0取自实际启动数据副本 `6002e3e4`。
三个readiness字节0、饱和日志计数100、计时器值和栈是合成现场：没有执行全启动，
没有为了继续推进而把所有未知MMIO映射为0。其他未建模入口/访问仍会停止。

缓存地址rx、非缓存别名rw是runner提供的映射；哨兵成功不验证硬件MPU、cache或跨核可见性。
底层NAND/DMA没有执行。启动前缀被作为已驻留代码提供，reset-ROM如何选择和装载它
仍未证明。后续覆盖、全部引用和代码所有权也不由这项回放关闭。

所有标记只在进程内fixture；没有改写原厂输入、解码文件或生成升级包，没有SHA。
[结构化结果](../../research/ep7/early-load-probe.json)记录三轮加载（成功、重载、失败）
及两次哨兵调用。两处 `approved_for_placement` 仍为false，G6/G8未放行。
