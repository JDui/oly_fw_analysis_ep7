# E-P7 加载段与代码放置约束

2026-10-31。G6 的第一批原生驻留证据。复用现有 E-P7 输入/objdump 检查器和
仓库按 loader/table 追踪的研究方法；PEN-F 地址、启动场景和空闲区域没有移植过来。
本批没有选定注入地址、修改镜像或启动整体固件编译。

后续[早期代码承载审查](EARLY_CODE_SPACE.md)已筛出两个早期加载的32,640字节内部
候选，并记录有限引用分类及600201fe冷初始化候选接续；尚未批准覆盖或执行。

## 九段表与早期搬运是不同加载路径

原厂表60027068有9个12字节行，字段为 decoded start、logical flash source、RAM
destination。start与destination在本输入中相同。结束地址由60045786的9路跳表选择，
**不是下一行的start**。600457e7使用 end-start，转换地址后调用6005bc79，操作值0x101。

|---:|---|---|---|---:|
|1|600d7800|60211000|40757800|1,284,096|
|2|60280800|6055e800|40900800|3,006,464|
|3|6057b200|605b7800|40bfb200|247,296|
|4|605baa00|60748000|40c3aa00|1,627,648|
|5|6075a800|60b9e000|40dda800|4,470,784|

表索引包含 GNU 命名的udfu01/udf00立即数12，本批核对其指令、行结构、分派值和
地址关系，没有执行或赋予自定义指令完整语义；此表是静态加载配方，不是启动回放结果。
段8的计算长度为0，也不表示它或它前后的区域可用。

在RTOS入口60020392之前，600200f9还直接经6002144e执行下列搬运。
RAM的a0/a1别名按原厂调用记录，缓存行为没有在硬件上验证。
后续[原生控制流回放](EARLY_LOAD_EXECUTION.md)确认首项的三段读取；也确认底层返回错误
时6002144e仍可清D0返回。下表是搬运请求范围，不能用包装器的0返回值证明实际完成。

|解码源范围，不含结束|RAM目标|字节数|用途/约束|
|---|---|---:|---|
|60030000..600d0800|a0030000|657,408|包含kernel hooks、原生loader和RTOS代码|
|60230800..6025eb50|a1f98540|189,264|已有UI资源指针表也来自这一初始化数据段|

|60278800..60278804|a1fe0540|4|独立初始化数据|

还存在明确的**段9之外占用**：60020272从flash41abca00搬运6144字节至a143ca00，
再从那里复制1536个word到47000800。对应解码范围是6143ca00..6143e200。
因此，把段9之后一大片区域直接视为尾部空洞会覆盖已有启动helper。
60045097另将flash41f9ffe0的32字节读到6191ffe0；该地址恰好是decoded payload
结束，不能把容器尾部算进可放置的payload。

## 现有候选跨多个驻留阶段

|候选部分|原厂驻留来源|
|---|---|
|raw queue receive/send/delete三个inline hook|早期60030000..600d0800搬运|
|capture初始化、39个CALL、producer、descriptor/worker、CPU COLOR builder|段2|
|GUI allocator60a4ec03|段5|
|GUI041d、输入处理、service/display vtable、文字模板|段6|
|61fb7070资源指针表、61fc3874父回调表|早期初始化数据搬运，指向后加载代码/资源|

这带来明确的冷启动约束：把所有自有代码放到一个晚加载段，不能直接让早期kernel
补丁跳过去。即使共享runtime尚未发布，执行C中的空slot判断也要求该C代码和slot存储
已驻留且初始化。先写了某个RAM hook，后续原厂段复制还可能覆盖它。

尚未证明首个controller/GUI使用点相对段加载、构造器和其他CPU任务的完整先后。
安装器应区分文件中的补丁随原厂加载生效，以及启动时修改RAM的补丁；不能靠一个
布尔installation_ready掩盖这两种不同的生效顺序。

## 两类完成状态与范围配置

600457e7在存储调用后设置a272e420的相应bit。读取非零状态的本地分支先调用诊断；
**若诊断返回，仍能到达该bit写入**。本批没有证明诊断一定不返回，所以不能用这个
标志独立证明所有字节都已成功加载。

6004586c等待上述bit，再更新ordinal a272e424，进行范围配置及各段初始化调用，
最后才置另一组bit a272e41c。范围配置60058c66的特定分支把边界写入99700058/
9970005c；6004595c使用第一段destination和第9段end作为完整范围的两个边界。
硬件权限、cache刷新及跨CPU可见性尚未确认，报告没有将寄存器写入解释成已验证的写保护。

因此，改变段的长度可能同时影响读取长度和范围配置；冷安装必须审核两条链。
“加载标志已置位”“段构造已返回”“候选完整安装并可见”是三个不同条件。

## 当前短CALL约束已从实现提取

后续更新：[远跳桥](FAR_CALL_VENEERS.md)已为捕获侧18处选定五字节JMP32加独立建帧桥。
下面区间是保留原CD CALL时的约束，仍是原始测量结果；新方案无需在这些区间内寻找
adapter落点。代码驻留、最终重定位与完整安装仍须资格化。

[探针](../../tools/ep7_load_regions.py)读取实际controller_sidecar/cohort.c的39项，
核对本输入每个CALL的宽度、register mask和frame，再按16位有符号位移取每组交集。
宽CALL保持原7字节，短CALL保持原5字节，未覆盖邻接指令。

|短CALL目标组|共同可达起点..终点，均包含|
|---|---|
|state transition|60281d02..60291c5d|
|engine pool|60294e9d..602a4e9c|
|engine configure|6029a7e4..602a6f4b|
|associated reset|60294692..602a4691|
|fresh|6029c480..602ab1c6|
|sample|6029c4a3..602ab1e9|
|finish|6029c4b5..602ab1f6|
|wait scope|602a466c..602b44fc|

单个公共短跳落点不存在。覆盖这8个区间至少需要2个数值位置；这是区间交集的数学
下界，不是两个合格code cave。桥实际大小、独立入口、原生控制流、回跳、覆盖区间和
cache仍须逐个处理。把主代码挪到远处不能自动解决这些短CALL。
