# 次核等待前的原厂调用闭包

此前冷启动审查保留了一个具体疑点：CPU1/2在等待共享启动字之前都会调用
`60054a7a`，不能仅凭等待循环认定它们不接触堆。现在已沿这个完整短调用链核对，
并用既有严格GNU引擎从两个实际次核入口执行到等待点。

## 原厂函数做什么

|函数|可达指令数|作用与调用|
|---|---:|---|
|60054a7a|16|输出零结尾字符串；换行前输出CR；两处CALL都到60020429|
|60020429|23|按8ff0005c选择UART，等待状态非零，输出一个字节；调用60023637|
|60023637|11|可选地将字节追加到诊断环形缓冲区；无其他调用|

复用 `NativeGraph` 的可达控制流和CALL/RET frame检查：只显式开放这三个函数的
精确区间，跟踪所有条件分支。3条CALL边、所有正常返回的frame匹配，没有间接调用、
未闭合控制转移或allocator调用。原来的kernel默认搜索范围保持不变。

诊断函数首先读 `a26a4a58`。为0时直接返回；非零时从 `a26a4b40` 取buffer指针、
从 `a26a4b44` 取半字索引，写一个字节，再将索引加1并与8191相与。
**没有allocator调用不等于没有通过指针写内存。** 启用诊断时，这个buffer仍有独立
所有权要求；没有把该分支隐藏或默认设为安全。

启用字的cached别名 `626a4a58` 落在已核对的第二处启动清零请求
`621caf00..62796888` 内。本批重新核对该清零请求的3条指令，但未执行清零DMA，
没有由请求范围推导实际清零完成或没有其他写入者。

## 两个实际入口的有界执行

显式fixture只提供：本核寄存器存储、UART selector=0/ready=1、diagnostic flag=0、
共享release字和本核栈。堆、拟保留payload、guard和诊断buffer均不映射，未知访问会停止。
UART地址来自本输入 `60023e30/34` 的原厂表，未替换输出函数或任何callee为成功stub。

|次核|入口|实际输出|到达等待点|原生指令数|
|---|---|---|---|---:|
|CPU1|60027117|`1`|60027219|81|
|CPU2|60027575|`2`|60027624|81|

两个入口均自行把SP设为 `470007fc`，随后保留4字节调用槽；到等待点时SP为
`470007f8`，最深为 `470007e8`，即已建立栈以下20字节。第一条AND之后IE/LM保持0。
这只是这段入口路径的深度，不能代替Usr3或整个固件的完整栈界。

从同一执行后现场各续跑两次：release=0时三条原指令返回原等待点；release=1时
三条指令走到 `60027223` / `6002762e`。后续1536-word helper复制和kernel启动未执行。
共6次短引擎调用，157个精确解码地址；本批没有重跑对象编译或无关测试。

## 对G6的影响

关闭的是“已知等待前函数中是否还隐藏allocator调用”这一有限疑点；在给定冷现场中，
两条次核入口也确实没有访问堆或保留区。诊断启用分支、实际冷清零完成、硬件复位/启动、
release跨核可见性、IRQ/NMI及启动前缀装载仍是未决条件，未宣称全核静止或区域可用。
