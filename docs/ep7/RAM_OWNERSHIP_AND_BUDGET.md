# E-P7 启动 RAM 所有权与候选预算

2026-10-31。继续 G6：用 E-P7 自身的清零调用、分配器、释放器和守卫表
界定已有占用，提出一个可审查的私有 RAM 保留方案。没有修改原厂输入、
运行相机代码或选定已获准的注入地址。

## 启动写入和 kernel arena

`60020059`、`60020074` 是当前 main 中指向 `6002046d` 的两处有限 CD/DD
编码候选，参数已逐指令核对。该函数先把起止地址归一到 `a0/a2` 地址别名，
用 end-start 计算长度；大块走 `9c1000xx` DMA 描述符，小尾段有实际清零存储。
DMA 没有执行，不能据此声称真实 RAM 已经清零。

|621caf00..62796888|6,076,808|第二次清零调用；起止操作数分别使用不同别名，函数内归一|
|61b20fe0..61b218a8|2,248|60020117..137 从 6002e020..6002e8e8 逐 word 复制初始化数据|
|6203c940..620ed940|724,992|domain0 kernel 配置 +44/+48|
|620ed940..6215d940|458,752|domain1 kernel 配置 +44/+48|

`600360b5` 从 `8ff00004` 的当前 domain root 读取 +40 的管理对象、+44 的
arena 起点和 +48 的长度，在首块和管理对象建立链表/长度字段。这些 arena
已有原厂分配责任，不能因文件中无初始化数据而拿来当候选 BSS。

完整 RAM 版图还包括[加载段报告](LOAD_REGIONS_AND_PLACEMENT.md)中的早期搬运、
九个段和 helper。本表是已发现的排除范围，不宣称覆盖所有 DMA/动态地址写入。

## 原厂分配器不是任意大小的 heap

`60022700` 按请求大小选择固定池：最多128、2048或16384字节。更大的请求走
诊断后返回空指针的本地路线；本批不假定诊断必不返回，也不承诺普通分配不会失败。
每个槽的 stride 是 payload+64，不能把这64字节作为额外可用空间。

缓存地址池 `600228b6` 按 `8050` 区分三个 domain；释放器 `60022b23` 使用
对应 domain 的同组边界、槽数及位图。分配先消耗递增索引，再复用归还的槽号。
释放检查 stride 整除、非负、槽号上界及实际分配 bit，再把槽号加入回收栈。

|payload / stride|三 domain 连续总范围|domain0 / 1 / 2 槽数|
|---|---|---|
|128 / 192|61b21fc0..61bce7c0|3040 / 320 / 320|
|2048 / 2112|61e85800..61f8d800|448 / 32 / 32|
|16384 / 16448|61bd6d40..61dd8d40|64 / 32 / 32|

另外四个非缓存地址池由 `60026df4` 起点表、`60026e04` 槽数表和共用 stride
表驱动，`60022a61` 另有原生锁调用。它们也是已有占用：

最初静态批次核对自定义 `udf00` 索引操作数和各表的长度一致性，没有执行该操作码、
原生锁或并发分配。不能把这里的静态责任表当成跨核互斥验证。
后续[原生边界回放](POOL_RESERVATION_EXECUTION.md)已在GNU模型中执行domain2大块池的
`udf00`/DIV/位图及pre-kernel PSW helper；调度器激活后的锁和硬件并发仍未验证。

## 具体保留方案：只取末槽 payload，保留守卫

可进一步审核的方案是把 domain2 的大块池从32槽缩成31槽。
这样可从已有分配责任中明确划出最后一个 payload：

- 候选私有区：`61dd4d00..61dd8d00`，16,384字节。
- 原厂守卫：`61dd8d00..61dd8d40`，64字节，保持其原有责任。
- 分配上界：`600229b9` 的 `mov 32,d0`，拟改为31，编码 `8020` → `801f`。
- 释放上界：`60022c28` 的 `mov 32,d3`，拟改为31，编码 `8f20` → `8f1f`。

`60026f38` 的七行守卫表仍把整组大块池记为128槽。实际检查循环
`600fad97..600fae10` 只读取每槽 payload 后的16个 word；因此，只使用上述
payload 并保留64字节守卫，不要求为了本方案改动该检查表。改变整段 stride、
把守卫覆盖为候选数据或从 domain0 池中间切洞，都不属于这条方案。

**这两项仍是提案，没有写入固件。** 准入前还必须满足：

1. 两个上界位于60022xxx启动前缀，**不在60030000起的kernel复制范围内**；修改必须
   随启动前缀的原厂加载生效，先于任何原厂分配。不得把它们延后到kernel复制或活跃池里缩容。
   后续原生执行发现：回收分配不重新检查槽号，旧回收栈中的31仍能返回待保留地址；
   这是晚安装不可用的具体反例，不能通过清空活跃池状态绕过。
2. 候选区不在已查明的原厂清零范围内，必须显式清零完整自有 `.bss` 和 cold storage，
   然后才能让任何候选 C/全局 slot 被访问。
3. 代码自身已驻留，先后顺序覆盖其他 CPU 启动；没有把“slot 还没发布”当成存储已初始化。
4. 继续排除绕过该分配器的直接使用，记录 CPU2 少一个大块的运行容量影响。
   本批没有做缩容后的实机负载测试。

报告中的 `approved_for_placement` 保持 false。此方案比“发现 FF 就选地址”
多了明确的原厂所有者和可核对的变更边界，尚不能替代完整冷安装资格。

## 存储量足够，但不是链接后的最终预算

复用已有 pipeline/UI 对象尺寸报告，按源文件去重并剔除两个 ABI caller probe。
本批最初得到95个实现源文件、text43,587字节；后续[完整远跳接合](REMAINING_FAR_CALLS.md)
重新检查pipeline/UI对象后，曾为101个实现源、未链接text44,793字节。随后计入清零桥和
[流水线安装组](PIPELINE_INSTALLATION_COHORT.md)，当时为104个实现源、text45,733字节、data为0、
BSS2,376字节。最新加入[一次性bootstrap](COLD_BOOTSTRAP.md)后为107实现源、text46,543、
data0、BSS8,084；实际core/boot/runtime5704和once状态4均已包含。预算工具本身不重编这些实现；它们不含完整installer，
也没有作最终节对齐和全栈计算。

只额外编译了一个 `sizeof` 探针，使用当前头文件和既有 MN103 GCC13.4：

|当前目标类型|字节数|
|---|---:|
|ep7p core|5,052|
|ep7b bootstrap|72|
|ep7r runtime|580|
|三者组成的 cold storage|5,704，alignment4|
|当前全部生产 BSS 粗计|8,084，包含cold storage和once状态|
|16 KiB候选区剩余粗计|8,300|

此前用5,704字节类型探针补足尚未实例化core/runtime的预算；现在它们已在生产BSS中，
不能再重复相加。预算工具核对实际实例尺寸与当前类型一致。
不把8,300字节当可任意分配余量：链接对齐、安装器状态、队列配置增加的
原厂 backing、完整嵌套栈与预留都要单独计入。
